## Findings on the delivered helpers (ranked; each reproduced unless marked code-read)

### T1 (blocking for the wiring) - the plan renames the scenario's links, so the packet's scenario fails the packet's netns preflight

Code: `topology.rs:119-185` (generated ids `{front}--{node}`, `{front}--storage-{pool}`, `{miner}--{front}`; only node-to-node scenario links are kept by id, everything else is silently dropped; `consensus_link` keeps only the last node-node link), `links/netns.rs:117-135`.

Counterexample (probe P4): `TopologyPlan::from_scenario(lab-topology-two-nodes.json)` yields links `front-a1--node-a, front-a1--storage-pool-a, front-b1--node-b, front-b1--storage-pool-b, miner-a--front-a1, miner-b--front-b1, link-p2p-nodes`; the scenario declares `link-alice, link-bob, link-pool-a-node, link-pool-b-node-b, link-p2p-nodes`. `NetnsLinkBackend::preflight(&scenario)` against a broker started from `plan.broker_spec()` -> `Unavailable("the namespace broker did not publish link link-alice")`. Fail-closed, but it means no scenario fault on a miner-front or pool-node link can ever be applied through this backend, and `validate_links` (which requires every miner->front and pool->node link to be named) guarantees every real scenario hits it.

Fix: use the scenario's link ids verbatim for every scenario-declared link (the plan may *add* storage links, never rename), fail `from_scenario` on a scenario link that maps to no planned pair, on duplicate generated ids, and on more than one consensus link (make `consensus_links: Vec`). Test: `preflight` of `lab-topology-two-nodes.json` against its own `broker_spec()` must pass; a scenario link whose endpoints are not planned must fail `from_scenario`.

### T2 (blocking for the wiring) - `NamespaceBroker::start` accepts a stale manifest as the new broker's

Code: `namespace.rs:255-272` (waits for `manifest.json` and `control.sock` to *exist*, reads the manifest, no `run_token` comparison, no `ping`, no `up-error-*.json` check).

Counterexample (probe P1): start a broker in `run1`, SIGKILL it (stale socket, manifest, lock remain), then `start` again in `run1` with token `aaaa0002`: returns `Ok` after **7 ms** with `manifest.run_token == "aaaa0001"` (the dead broker's holder PIDs) and `ping -> Unavailable (Connection refused)`. This is the same false-ok I sent back in LP-4a N1, now on the Rust side; `link-fault.sh` fixed it (token match + ping handshake), the Rust client did not inherit the fix. The stale test directories under `/tmp/lp-topology-*-237817/broker/` (from the candidate's own earlier runs, `up-error-lp-topology-token-bypass.json`) show the second failure mode: a non-hex token makes the broker fail at veth creation (`"name" not a valid ifname`), and the client only reports it through the log text.

Fix: refuse a non-empty `broker_run_dir` (mirror `link-fault.sh`'s `stale_run_dir`), validate `run_token =~ ^[0-9a-f]{8}$` in `BrokerOptions`, require `manifest.run_token == options.run_token`, return the `up-error-<token>.json` payload as `Broker(..)` when present, and complete `start` with a successful `ping` whose `token` matches. Test: the SIGKILL-then-restart sequence must return `Err`, never a manifest with a foreign token.

### T3 (should fix) - `NetnsLinkBackend` error mapping and `current()` cache

Code: `links/netns.rs:137-162`.

Counterexamples (probe P2): `apply` on an unknown link -> `Unsupported("netns" does not support policy partition)` (the broker said `unknown_link`); `apply` of `latency 0` -> `Unsupported` (fine) but every broker rejection (`policy_apply_failed` with a `partial` half-state, `namespace_gone`, `busy`) is folded into `Unsupported(policy)`, which the engine will read as "this backend cannot do partitions". After SIGKILL of the broker, `counters` -> `Unavailable` (correct) but `current(ab)` -> `Some(Partition)` although the namespaces and rules no longer exist. The report's "the backend reports Unavailable afterwards instead of a stale answer" is true for RPCs, not for `current()`.

Fix: map by broker error code (`unknown_link` -> `LinkError::UnknownLink`/`Unavailable`, `invalid_policy` -> `Unsupported`, `policy_apply_failed`/`partial` -> a new `LinkError::Partial` carrying the broker detail, `busy` -> retryable); on any apply error clear the cache entry; have `current()` consult `status --link` (or invalidate the cache when the last RPC failed) so a dead broker yields `None`, and document that `None` means "unknown", not "normal". Test: apply, kill broker, `current()` must not return a policy.

### T4 (should fix) - exec handshake: symlinked programs time out, launcher failures are misreported, killed launches are never reaped

Code: `supervisor.rs:254-269, 298-316, 639-661`.

Counterexamples (probe P3, inside the broker user namespace): (a) `program = /usr/bin/python3` (a symlink to `python3.10`) with a namespace -> `ExecHandshakeTimeout` after the full `ready_timeout_ms` (3.0 s), while the same program *without* a namespace records `/usr/bin/python3.10` and succeeds; any `result/bin/..` or other symlinked path will fail the same way. (b) `namespace = /proc/1/ns/net` (not owned) -> `nsenter` exits at once with `cannot open /proc/1/ns/net: Permission denied` (in the log), but the supervisor waits the whole deadline and reports `ExecHandshakeTimeout` instead of the launcher's exit status. (c) both failed launches were `kill()`ed but never `wait()`ed: two zombies remained under the supervisor until `stop_all`.

Also code-read: the handshake trusts the published `netns_path` (`/proc/<holder>/ns/net`) without checking the holder's `start_time_token` from the manifest; a recycled holder PID would be refused by the kernel (`EPERM`, the netns would belong to another user namespace), so it fails closed, but the error would again be the misleading timeout.

Fix: compare `fs::canonicalize(expected)` with `/proc/<pid>/exe`; inside the wait loop call `child.try_wait()` and return `ExitedDuringReadiness { status }` immediately; `wait()` after `kill()`; verify the holder token before launch and return a distinct error. Tests: symlinked program succeeds; unowned namespace fails in < 100 ms with the launcher's status; no zombie after a failed launch. **There is currently no test of `in_namespace` at all** (the only call sites are the report and my probe); add one to `topology_namespace.rs` running the supervisor inside the broker user namespace via `join_command`.

### T5 (should fix) - `CanonicalObserver` turns a non-atomic tip read into a false displacement

Code: `topology.rs:313-337` (the tip pair is recorded as observed without checking that `hash_at(height) == hash`), report section 8 item 7 (recommends `tip = getblockcount + getbestblockhash`, two RPCs).

Counterexample (probe P5): a probe whose `tip()` returns `(count-before-block, hash-after-block)` once -> the **first** observation at height 10 is `no` ("tip displacement observed") with no reorg anywhere. In the runtime the two RPCs race with every new block, so this will fire in a live run.

Fix: define `CanonicalProbe::tip` as an atomic view (`getbestblockhash` then `getblockheader(hash).height`, or re-read `hash_at(height)` and only record when it equals the tip hash; otherwise skip this pass as `unknown`). Test: the racy probe above must produce `unknown`/no record, never `no`. Keep the `tip_sampler` scope label; this observer is still a tip sampler and must not be described as reorg coverage (the report mostly already says this).

### T6 (gate) - the new tests are unconditional and tool-dependent, so they break the Nix `test` check

Code: `crates/spc-lab/tests/topology_namespace.rs:41-54` (`tool()` falls back to `/usr/bin/<name>`; no `#[ignore]`, no capability guard), `flake.nix:91-98` (`checks.test` runs `cargo test --workspace` with no `iproute2`/`nftables`/`util-linux`/`python3` in its inputs). Every other host-dependent proof in this crate is `#[ignore]`d with an environment variable (`real_node_proof.rs:15`).

Evidence: `nix build --offline .#checks.x86_64-linux.test` from the git-metadata-free source copy (`/tmp/opencode/Fable-topology-nix-test.log`, full log `Fable-topology-nix-test-full.log`): the derivation **fails** after 3 m 22 s. Every pre-existing test binary passes (45 `test result: ok` lines, the approved host's 609-test surface is intact), and `tests/topology_namespace.rs` reports `FAILED. 2 passed; 8 failed`: the eight broker-backed tests panic with `the namespace broker starts: Io(NotFound)` (no `unshare` in the sandbox) and `host_address_collection_returns_addresses_not_interface_names` panics at line 712 because `/usr/sbin/ip` does not exist. On this snapshot the approved host's green Nix gate is red.

Fix: gate the ten process-level tests on an explicit opt-in (`SPC_LAB_NETNS_TESTS=1` or a preflight probe that returns `inconclusive` when `unshare`/`nsenter`/`nft`/`ip` are missing) and make them `#[ignore]` by default like the other proofs, or give the flake an opt-in `checks.lab-topology` with the tools and a user-namespace-capable sandbox. The default `nix flake check` must stay green.

### T7 (should fix) - host-path and environment assumptions in the broker client

- `namespace.rs:412` hardcodes `/usr/sbin/ip`; `start()` resolves `python3` from `PATH`; `BrokerOptions::new` defaults to `/usr/bin/unshare` and `/usr/bin/nsenter`. Under Nix none of these exist. Worse, when `ip` is missing `host_global_addresses()` returns empty lists silently, the broker receives no host addresses and the host-unreachability dimension of `no_bypass_check` passes vacuously. Resolve tools from `PATH`/options and make an enumeration failure an error (distinguish "no global addresses" from "no `ip`").
- `request()` uses one connection per request with a 300 s read timeout and an unbounded `read_line`; fine with the broker's 256 KiB cap, but bound it.
- `Drop` kills the broker without `down`; cleanup relies on the PDEATHSIG chain (verified to work) and leaves a stale socket/manifest, which is what T2 then mis-reads.

### T8 (design gap to resolve before wiring) - the storage boundary as described is not implementable with the current pool

Report 2.2 and 6: "the storage actors stay outside the lab namespaces and are reached by the front over the private Unix socket .. or over the loopback of the storage endpoint". The loopback of another namespace is not reachable from the front's namespace, so that option is not real. A Unix socket works across network namespaces, but `grep` of `crates/spc-store` and `bins/spc-pool` finds no Redis Unix-socket support (0 files mention `unix`); only PostgreSQL has one. Meanwhile `TopologyPlan` creates a `storage-<pool>` namespace and a `Storage` veth that nothing will inhabit. Decide and implement one of: Redis over a Unix socket (pool/store change), a per-pool storage process inside the storage namespace with a non-root uid mapping (the report says `EINVAL` on this host; record the kernel/`newuidmap` facts), or drop the storage endpoint from the plan and state that storage is host-local. Until then, the two-pool scenario cannot run in namespaces.
