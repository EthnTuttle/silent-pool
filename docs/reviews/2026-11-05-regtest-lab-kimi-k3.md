## Overall verdict

**Sound skeleton; one near-fatal omission and one incorrect baseline figure must be fixed before P0 closes.** The plan's central discipline - node-authoritative difficulty, real PoW, capability preflight, independent policy oracle, privacy boundary, run artifacts - is correct and well argued, and its own source audit is mostly accurate. But:

1. The plan never engages with the pool's share *credit* formula, only its target policy. `credited_difficulty = min(share_difficulty, max(1, round(network_difficulty(bits))))` (`bins/spc-pool/src/sv1.rs:108`, decision 2026-11-02 §3) means that under any fractional share-difficulty regime, whenever network difficulty rises above 1, credit is clamped to the *pool policy constant*, not to the share's actual work. That is exactly the "equal credit per submission at different share targets" outcome §3.3 says "must" not happen. The §3.3 open decision is therefore not open: any fractional-work resolution forces an accounting decision record touching SPEC §4.3. P0 must be reframed accordingly.
2. The plan's only numerical anchor - "`0x200fffff`, roughly 16 hashes per block" - is wrong by 16x: 2^256/(T+1) = 256. And its more important claim, that "ordinary regtest inherits 600-second spacing," is wrong in the way that matters for the lab: rust-bitcoin's `BtcParams::new(Network::Regtest)` keeps Core's `pow_target_spacing = 600`, but the plan relies on that while also planning *shortened* lab schedules. Since the in-process test override sets `pow_target_timespan = k * pow_target_spacing`, the adjustment-interval arithmetic the lab will use is a test-harness mutation path (`params.btc.*`), **not** an exposed, validated multi-process node configuration - rbitcoin-node's config exposes only `--regtest-pow-bits` and activation overlays (`crates/rbitcoin-node/src/config.rs:497-498, 777-780, 1631-1634`; no `no_pow_retargeting`/`allow_min_difficulty_blocks`/`pow_target_spacing` knobs anywhere in `config.rs`). P0's "verify the exact rbitcoin build and obtain a tested retarget-capable profile" is a real node-code deliverable, and the plan should say so in one blunt sentence: today there is no way to launch an rbitcoin binary that retargets, because the two consensus flags that enable it are not reachable from any config key or CLI flag.

Severity classes: B1 = plan defect (wrong/unsupported claim or missing requirement), B2 = existing implementation blocker acknowledged or unacknowledged, E = optional enhancement.

## Ranked findings

### F1 (B1, §3.3 + §8/P0 + §9 Q2) - Share-target-vs-credit asymmetry makes the "open decision" not open

- Evidence: plan line 159-161 ("Different share targets must earn work-proportional credit, not equal credit per submission. Preserve the SPEC §4.3 window semantics (`N x d`)"); `bins/spc-pool/src/sv1.rs:108` `credited_difficulty(share_difficulty, bits) = share_difficulty.max(1).min(network_difficulty(bits))` with `network_difficulty` measured against the difficulty-1 target; decision `docs/decisions/2026-11-02-share-target-policy.md` §3 and §6 ("The same `d` is used everywhere in accounting ... `d` is never 0").
- Defect: on any chain with network difficulty > 1, credit per accepted share is `min(share_difficulty, round(D_net))`, i.e. the configured constant - independent of the share's announced target once `share_difficulty <= D_net`. Under the fractional-work regime §3.3 proposes (CPU-scale targets far easier than difficulty 1), every share still credits exactly 1 (since `max(1, round(D_net)) >= 1`). So "work-proportional credit" and "d is never 0" are mutually incompatible under fractional difficulty: proportional credit for a 1/256-difficulty share requires crediting 1/256, which violates the integer `d >= 1` invariant. One of the two quoted requirements has to give, and giving up `N x d` semantics is a normative accounting change. The plan cites §4.3 as a constraint to preserve but does not identify that preserving it forces the "documented regtest-only work-scale profile" branch and *still* requires a decision record (the current decision is "d is never 0").
- Suggested fix: rewrite §3.3's open decision into a closed requirement: (a) the lab profile fixes network difficulty below 1 for the entire run (pow limit / `regtest_pow_bits` chosen so `round(D_net) == 1` always), making per-share credit uniformly 1 and `N x d` unchanged; OR (b) adopt fractional `d` with an explicit decision record amending SPEC §4.3's `N x d` and the `d is never 0` invariant. State that (a) is the P0 default and (b) is out of scope for v1. Also state the corollary: under (a), "work-proportional credit across different share targets" cannot be tested at all, so VarDiff/per-channel targets are deferred, which the plan already half-says.
- Falsifiable acceptance test: P0 gate artifact names the chosen branch. Under (a), a run fixture sets `share_difficulty = 1` on retarget-capable regtest and the oracle asserts every accepted share's `ShareRec.d == 1` *and* the frozen window's `N x d` equals the persisted `window_target`; under (b), a decision record exists and a mixed-target fixture credits two shares at distinct non-1 `d` values reconstructible from the recorded targets.

### F2 (B1, §2 line 60-61 + §3.2 line 104-107) - Wrong arithmetic on the baseline target; regtest spacing claim misleading

- Evidence: plan line 60-61 "uses `--regtest-pow-bits 0x200fffff`, roughly 16 hashes per block"; line 104 "Ordinary regtest inherits 600-second spacing". `testing/regtest-rbitcoin-e2e.sh:33`, `regtest-rbitcoin-reorg-e2e.sh:63`, `regtest-rbitcoin-tp-e2e.sh:42` all set `POW_BITS=0x200fffff`. rust-bitcoin `pow.rs:133` `MAX_ATTAINABLE_REGTEST = 0x7FFFFF00 << 96` (compact `0x207fffff`); `0x200fffff` => 2^256/(T+1) = 256.00 (verified by direct computation). rust-bitcoin `consensus/params.rs:106-109` regtest: `pow_target_spacing = 600`, `pow_target_timespan = 14d`, `allow_min_difficulty_blocks = true`, `no_pow_retargeting = true`.
- Defect: the "16 hashes" figure is off by 16x, and "600-second spacing" attributes to the regtest profile a spacing that only the *test override* (`pow_target_timespan = 4*600` etc.) shrinks; the stock profile has a 2016-block / 2-week retarget, so even if retargeting were enabled by default, a lab run would need ~2016 blocks per adjustment. The plan does mention "deliberately shortened lab schedule" as an option, but it understates the starting point: nothing short of mutating `params.btc` changes the interval, and no node config surface exposes it. This matters because §8/P0's acceptance ("reviewers can identify which component sets each target") cannot be met by pointing at config - today the answer is "a test helper in `rbitcoin-rpc/tests/methods/mod.rs:6281-6370`, not the node."
- Suggested fix: correct the figure to 256 hashes/block at `0x200fffff` (and 2 at `0x207fffff`), and add one sentence to §3.2: "No rbitcoin-node config key or CLI flag today enables retargeting or shortens the interval (`config.rs` exposes only `regtest_pow_bits` and `testactivationheight`); the retarget-capable profile is a code change to the node's config surface, not a discovered option." Reference `crates/rbitcoin-rpc/tests/methods/mod.rs:6330-6334` as the existing in-process precedent.
- Falsifiable acceptance test: `rbitcoin-node` built at the lab pin, launched with the documented profile flag(s), mines blocks 1..2k under sustained CPU hashrate with `getmininginfo` `next.bits` differing from `bits` at the first boundary height; launching the same binary without the flag keeps constant bits. The flag set is listed verbatim in the run manifest.

### F3 (B2, §5.1 bullet list) - Merkle branch orientation is unchecked end-to-end; the listed gaps miss it

- Evidence: plan lines 281-283 list missing nonempty merkle-path vectors and byte-order checks but not orientation. `bins/spc-pool/src/sv2_server.rs:287-291` folds branches with `.rev()`; `bins/spc-pool/src/sv1.rs` presumably matches its own SV1 notify order; rbitcoin TDP supplies `merkle_path` from `getblocktemplate`'s `merklebranch`, which Bitcoin Core documents as deepest-first (concatenate coinbase, then branch[0], ...). `rbitcoin-consensus/src/regtest_pad.rs:283-285` uses `compute_merkle_root()` (natural order) - so `template_tp.rs` and `template_rpc.rs` may disagree with each other on orientation for non-empty tx lists, and no test with a non-empty list exists (`e2e_sv2.rs:38` `merkle_branches: vec![]`; plan line 270 confirms "use empty transaction lists").
- Defect: §5.1's gap list is a source audit presented as complete ("Source inspection identified these prerequisites"), yet the highest-probability silent-failure item for the "Introduce transactions" command (§5.2) - branch order - is absent. A reversed branch yields a wrong merkle root that still meets the share target, is credited, and then fails node block validation: precisely the "ingress success precedes acceptance" hazard the plan calls out, one layer down.
- Suggested fix: add to §5.1 gap list: "Verify merkle-branch concatenation order against Core GBT semantics on a template with >= 1 non-coinbase transaction for both `template_rpc` and `template_tp`; the two sources must produce byte-identical jobs for the same template."
- Falsifiable acceptance test: P1 acceptance adds: a fixture block with >= 3 transactions mined through the SV2 path is accepted by the node (via both template sources), and the pool-credited share's reconstructed merkle root equals the header's - a deliberately reversed branch must be rejected at the front's block-assembly check.

### F4 (B2, §5.1) - No miner-initiated work-refresh path: nonce-range exhaustion cannot be satisfied within a job

- Evidence: plan line 250-251 "renew work on exhaustion"; `sv2_server.rs` message dispatch handles only SetupConnection/OpenExtendedMiningChannel/SubmitSharesExtended (lines 164-351) - no `NewWork`/`SubmitHeader`-style refresh and, more basic, no mechanism for the miner to get fresh extranonce within a job. `miner_extranonce_size: u16 = 4` fixed (line 202). `front.rs` job ids derive from template state (`front.rs:676-680`), refreshed on `[template] refresh_interval_ms` (default 1000, `main.rs:284`), and `send_job` broadcasts every publish (i.e. also on fee-level churn).
- Defect: with 2^32 nonces + 2^32 miner extranonce per job, a multi-GH/s CPU miner (plausible on one modern socket with midstate reuse) exhausts a job in well under the 1 s template-refresh cadence *when the template does not change* (only `(height, prev_hash, fingerprint)` changes trigger republish, decision 2026-11-02 (e) §5). The miner's only correct behavior then is to stop, making achieved-hashrate measurements cadence-bound rather than CPU-bound - silently violating §7's "achieved work and saturation" measurement goal. The plan's "renew work on exhaustion" has no protocol to renew over.
- Suggested fix: add an explicit P1 prerequisite: either negotiate `min_extranonce_size` from the client (`sv2_client.rs:115` sends 0 and is ignored; server hardcodes 4) with the front's `extranonce_len` enlarged accordingly (touches SPEC §2.4.1's scriptSig budget - flag as decision-adjacent), or define a pool-extension "more work" request, or document a hashrate ceiling per channel (`2^64 / min_job_lifetime`) as a measured capability bound. Note the interaction: any change to the 4+4 layout also changes `identity.parse`/`extranonce` invariants tested in `e2e_sv2.rs:278-284`.
- Falsifiable acceptance test: a single miner at a declared hashrate > 2^32 hashes/s-equivalent (simulated by a share target requiring ~2^20 hashes/share and a fast CPU) sustains >= 95% of requested hashrate over 60 s without stale-share or duplicate-share errors, with the job-id sequence recorded.

### F5 (B1, §4) - Topology model omits node count / TP session arithmetic; the "shared node sufficient" claim hides the constraint

- Evidence: plan lines 204-214; `rbitcoin-sv2/src/lib.rs:32` `MAX_SESSIONS: usize = 8`. The plan says "N miners connect to pools, not individually to node TDP" - true - but never states the binding arithmetic: each pool front using `sv2-tp` consumes one of 8 sessions per node, and the existing harnesses co-locate pool roles per node. With P competing pools on one shared node, P <= 8 TDP sessions (minus any JDS/other consumers), and with R nodes peering, each pool needs its own TDP session on its own node - the plan says "separate peered nodes are needed for ... partitions" but not that the 8-session cap is per-listener and therefore caps pools-per-node, not miners.
- Defect: minor but concrete: §4's "capability input" sentence should carry the arithmetic and a default (e.g. one TDP session per front per node; raise the cap in the rbitcoin profile as part of P0's node change - the same code change as F2).
- Suggested fix: amend §4: "The rbitcoin TDP listener caps sessions at `MAX_SESSIONS = 8` (`rbitcoin-sv2/src/lib.rs:32`); one pool front consumes one session per node. P pools on one node therefore require P <= 8 (minus JDS/TDP peers), and the lab profile should raise or parameterize this cap as part of the P0 node work."
- Falsifiable acceptance test: P3 acceptance: 9 pool fronts against one node's TDP listener either fail fast at preflight with the documented cap, or pass with the cap raised and recorded in the consensus-profile fingerprint.

### F6 (B1, §7) - "Mock node time ... not a generic speed multiplier" is under-specified where it matters most: retarget measurement

- Evidence: plan lines 382-391. `rbitcoin-consensus/src/clock.rs` mock time is per-process (`NodeClock.mock`), and `header.rs:196-199` rejects headers > 2 h ahead of the *node's* clock; `min_diff_gap` (`header.rs:294-297`) keys off *header* timestamps. The retarget algorithm consumes header times, so a lab can compress a 2-week timespan into minutes by setting block times ~600 s apart - but only via `setmocktime` coordination across R nodes, which the plan mentions once and never elevates to a P0/P4 requirement with ordering semantics (who advances time when; what happens to the pool's `refresh_interval_ms`, Ark round timers, mailbox epochs - all wall-clock).
- Defect: the plan lists time as a hazard but never assigns the fix: P4's "agreed timestamp and clock semantics across nodes" has no acceptance gate. Because retarget response *is* the headline experiment, a run where node A's clock is 90 min ahead of node B's will silently produce different `next.bits` on the same chain - a result-corrupting fault indistinguishable from consensus divergence.
- Suggested fix: add a P0/P4 requirement: the scenario vocabulary includes an explicit `advance_time(node|all, seconds)` command; every header timestamp the miners use is derived from the node's `mintime`/`curtime` (already true via jobs), and the oracle recomputes expected `bits` per node from recorded headers only. Runs that never cross a retarget boundary must not be labeled "retarget experiments" (the plan's preflight rule covers capability, not coverage).
- Falsifiable acceptance test: a declared retarget scenario asserts >= 1 observed boundary crossing with `|observed bits - oracle bits| == 0`; any run lacking a boundary event is reported "inconclusive", not "passed".

### F7 (E, §6/§8 P5) - Observation of block acceptance under TDP needs the node's chain view, not the TP stream

- Evidence: plan line 237 already states `SubmitSolution` is not proof of acceptance; decision 2026-11-05-sv2-tp-chain-view.md §2 keeps RPC as chain view. But §6's event list ("each node's tip/chainwork") does not pin the *minimum* acceptance evidence: `getblockcount`/`getblockhash` at the finding height + `getblock` coinbase read (decision §2 names exactly these RPCs). A reorg between tip-push and confirmation read invalidates a "block accepted" assertion made on the push.
- Suggested fix: in §6, define "candidate accepted at height H by node N" as: `getblockhash(N, H) == candidate hash` observed within a bounded cursor window; anything else is "submitted" or "tip-announced". Reorgs then naturally invalidate via the same predicate at later heights.
- Falsifiable acceptance test: P4 partition/heal scenario: an assertion "A's block accepted" made before heal is automatically re-evaluated after heal and flips to "orphaned" with no double settlement in the payout ledger (already a P3 gate - tie the observation predicate to it).

### F8 (E, §7) - Statistical framing: concretize "enough independent runs"

- Evidence: plan line 415-416. For the headline fairness claim (pool win share ~ hash share), with two pools at shares p and 1-p, distinguishing p = 0.5 from p = 0.55 at 95%/80% requires ~385 blocks *per effective sample*, and window-credit variance is dominated by the PPLNS window, not block count; the plan should bind sample sizes to the specific inference or drop the inference to "consistent with".
- Suggested fix: §7: "Each stochastic claim names its estimator, the null it rejects, and n (runs x blocks) before the run; otherwise the artifact records the metric as descriptive only." Cheap and falsifiable.
- Acceptance test: run manifest schema requires `statistics: {claim, estimator, n_planned}` for any scenario tagged `statistical`; CI rejects manifests with the tag and no statistics block.

## Corrections and dispositions (2026-11-05, post-review recomputation)

The original review above is preserved unchanged. On owner request I recomputed every contested claim with exact arithmetic and re-checked the contested source claims. Verified computations (Python `Decimal`, prec 60):

- Compact `0x200fffff`: exponent 32, mantissa `0x0fffff`, T = `0x0fffff << 232`. 2^256/(T+1) = **16.000015258803614...**. The original review's "256 hashes" figure was wrong (I had used mantissa `0xffff` instead of `0x0fffff`); the plan's "roughly 16 hashes per block" is correct.
- Compact `0x207fffff`: 2^256/(T+1) = **2.000000238418608...**.
- Candidate space per job: 2^32 nonce x 2^32 miner-controlled extranonce = 2^64 candidates = 1.8446744e10 s at 1 GH/s (~584.9 years at 365 d/yr), 1.8446744e9 s at 10 GH/s (~58.5 years). The original F4 claim that a multi-GH/s miner "exhausts a job in well under 1 s" was wrong by ~13 orders of magnitude.
- F8 derivation check (normal approximation, distinguishing p=0.5 from p=0.55 at power 0.80): two-sided 95% gives n = (1.960+0.8416)^2 * 0.25 / 0.0025 ~ **784.9 blocks**; one-sided 95% gives (1.645+0.8416)^2 * 0.25/0.0025 ~ **618.3**. The original "~385" was wrong for both tails (385 would be one-sided 90%/power ~0.5-ish, or a different effect size); the owner is right that the number as printed was unsupported.

Dispositions per finding:

- **F1 - PARTIALLY RETRACTED, one part survives as reframed.** The owner is correct that assigned difficulty represents *expected* work of the target (a submitted hash is 0/1 against the target; the difficulty is the expectation, not a realized leading-zero quality), so integer work scales with nonzero weights and formula `N x d` remain coherent, and the plan already flags any semantics/unit change as needing a decision record. My "requirements are mutually incompatible" framing overstated a logical contradiction. What survives, narrowed: the plan's branch (a) as I phrased it (keep D_net < 1 via `regtest_pow_bits`) does **not** by itself solve §3.3's stated goal of "frequent non-block shares," because the target clamp `max(target_for_difficulty(d), network_target)` (`sv1.rs:77`, decision 2026-11-02 §2) still makes every accepted share block-qualified whenever the network target is the easier one. The real open decision for the owner is whether `N x d` means "N shares" or "N network-block equivalents of work" (decision §6 already fixes `d = min(share_difficulty, max(1, round(D_net)))`, i.e. the former with a floor), and whether fractional `d` is ever wanted. That is an owner decision, not an impossibility assertion.
- **F2 - RETRACTED (arithmetic), one sub-claim survives independently.** The "16 hashes" correction is withdrawn; the plan's number is right, and my "600-second spacing is wrong" claim was also wrong - rust-bitcoin's `BtcParams::new(Regtest)` does keep `pow_target_spacing = 600`, exactly as the plan says (`consensus/params.rs:106`). - **F3 - STANDS, relabeled as verified where verified, allegation where not.** Verified on the current tree: `bins/spc-pool/src/sv2_server.rs:287-291` folds branches with `.rev()`; `e2e_sv2.rs:38` uses an empty `merkle_branches` list; `template_rpc.rs` builds `merkle_branches` itself (`template_rpc.rs:102` region) from the GBT response. A vestigial note survives: `sv2_client.rs:115` sends `min_extranonce_size: 0` and the server hardcodes 4 (`sv2_server.rs:202`), so the negotiated/requested extranonce sizes are still worth a wire-semantics check (already covered by the plan's own gap list, "Check requested/negotiated extranonce sizes").
